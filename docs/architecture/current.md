# Current architecture and evidence

**Working-tree evidence snapshot:** 2026-08-22, based on the current dirty worktree rather than a release candidate. CURRENT and PARTIAL claims describe inspected code and named passing tests; release completion still requires same-revision C0 and C6 evidence.
**Purpose:** record what the repository demonstrates, not what earlier plans promised.

## Model migration status (Standardized on Laya, 2026-09-21)

**PARTIAL:** The intended topology is now standardized on the **Laya Decision Engine** (~322M/421M non-autoregressive encoder, ~33ms latency) for local security, user-understanding, and semantic-analysis. Generative autoregressive Qwen models are deprecated and removed from the target local architecture; orchestration is assigned to an API LLM. Local egress checks and composable chat pipeline stages integrate directly with Laya without queuing delays.

Code: `packages/desktop/src/renderer/components/Markdown/richUi/`, `CodeBlock.tsx`. Tests: `tests/unit/chat/richUiSpec.test.ts`, `richUiBlock.dom.test.tsx`, `codeBlockPreview.dom.test.tsx`.

**PARTIAL:** End-to-end proof across all providers, mobile/web clients and packaged builds remains outstanding.

**CURRENT (2026-10-14 focused update):** Automatic presentation hints for ordinary explanatory/comparative turns now enter the shared native conversation send boundary via `common/chat/presentationGuidance.ts`; slash workflows are exempt. Fenced HTML renders directly within chat using an opaque-origin `iframe` with scripts enabled only inside the sandbox, offline CSP and a source-view switch (`Markdown/htmlPreview/`). ## Right-rail System Monitor (2026-10-15)

**PARTIAL (source + focused DOM/unit tests):** `HubRail.tsx` adds a persistent, closable `system-monitor` tab. `HubHome/monitor/HubSystemMonitor.tsx` uses the existing `useSystemMetrics` IPC subscriber only while the tab is mounted, showing system-wide CPU/RAM and historical trends, individual logical CPU cores, read-on-demand hardware snapshot (OS/CPU/GPU/disk capacity/network adapter count), and a searchable/sortable list of Tomni-owned Electron processes. Main already samples at 2 seconds while subscribed; no new privileged bridge/process-launch capability is exposed by this view. Hub Activity snapshot from `HubShell` supplies running and waiting-on-user Agent/Team/Schedule/App tasks separately. `systemMonitorModel.ts` bounds render counts and handles sorting/filtering. Tests: `tests/unit/renderer/guid/hubSystemMonitor.dom.test.tsx` plus `tests/unit/renderer/hubRailPreview.dom.test.tsx`.

**PARTIAL (2026-10-15, native Windows sampler proved):** `windowsTelemetryProbe.ts` now uses a fixed, non-interactive, size-bounded PowerShell command with CIM performance classes to read the **Windows-wide process inventory**, PhysicalDisk total read/write bytes/s, NetworkInterface aggregate receive/send bytes/s, and the greatest observed GPU engine utilization. `SystemInfoService` launches the asynchronous read-only probe only while streaming, no more often than 10 seconds, with a 7-second child-process timeout; Main merges optional, time-stamped results into renderer live metrics. Null means an unavailable counter, never fabricated zero. The system-wide process list can be switched with Tomni/Electron-only processes in the rail and is capped at 1024 bounded, validated names/PIDs. It is **stripped before the persisted or Agent-facing SystemSnapshot** and is never a process-kill interface. Focused privacy/cadence/parser tests: `tests/unit/system/windowsTelemetryProbe.test.ts`; renderer tests: `tests/unit/renderer/guid/hubSystemMonitor.dom.test.tsx`. Windows native command smoke on the project's Windows host: 274 process entries; GPU engine/disk/network counters present, ~2.2 seconds for a single probe. This verifies data-source availability on one machine, not an Electron UI smoke or cross-machine promise.

**SCOPE / TARGET:** The Windows CIM GPU **peak engine** percentage is a proxy

**PARTIAL (2026-10-15, Agent plane for the System Monitor):** the `tomny-system` stdio MCP server (opt-in, `enabled: false` in the catalog) now exposes a second read-only tool, `system_monitor`, beside `system_status`. It returns what the rail tab shows — per-core CPU, RAM, disk/network throughput and GPU-engine peak (Windows, only while the tab is open; otherwise `available: false` with a reason, never a fabricated zero), CPU/RAM trend over a bounded window, Tomni processes, data age (`ageMs`, `stale` after 20 s) and plain-language alerts. Source is the persisted `system-snapshot.json`; while a monitor viewer streams, `SystemInfoService` persists every 2 s tick and right after each telemetry probe (otherwise every 8 s). The snapshot carries only `MonitorTelemetrySummary` aggregates — OS-wide process names stay stripped. Code: `process/system/monitorReport/systemMonitorReport.ts`, `systemInfoMcpServer.ts`; tests: `tests/unit/system/systemMonitorReport.test.ts`, `systemInfoService.test.ts`. Not yet proven: Electron smoke of an agent calling the tool against the live app, and a catalog/Guide Map entry (the server is not in `BUILTIN_MCP_TOOL_CATALOG`, same as `system_status`)., **not** the aggregate GPU metric used by Task Manager; network interface totals can include virtual adapters. Other operating systems or Windows installations missing performance counter classes explicitly show unavailable, retaining CPU/RAM and Tomni process fallback. This remains read-only; full Electron UI, packaged runtime, privacy review of live IPC subscribers, cross-OS equivalence and optional-package boundaries are not yet release-proven.

**CURRENT (2026-10-15, bounded IPC and versioned SQLite):** Social IPC service limits account creation to 32, global sync to 8 accounts and cached conversation/message responses to 200. **CURRENT (2026-10-15 Web-only Feed UX):** A Facebook Web login showing the actual home feed does not populate the Social SQLite post queue because the shipped platform adapters are unavailable. The Feed now distinguishes Web-only unverified accounts from a genuinely empty authorized API feed and provides an account-specific **Reopen Web session** action (same persistent Electron partition); errors opening that window are visible. When no account is selected/available, the Feed directs users to Social Settings. This is navigation/read-only Web access, **not** ingestion of posts or credentials into Social. Evidence: `tests/unit/social/socialFeedWebFallback.dom.test.tsx`; official Meta APIs for Pages/own user posts must not be conflated with a user's personalized News Feed or personal Messenger inbox. Provider-approved OAuth scopes and credential configuration remain **BLOCKED** for real sync.



**CURRENT (2026-10-15 Web-session login revision):** The Social Settings **new account** action no longer requires a manually entered Facebook/other-provider handle: renderer invokes `social:account:connect`, and Main creates a local, unverified Web-profile with permissions initially disabled and launches the official provider login page in an account-owned `persist:social_*` Electron partition. The profile/partition identifier is stored in the existing Social SQLite account metadata (not an access token), so the **reopen Web session** action targets the same partition on subsequent app launches. Duplicate windows for one account reuse the same Web window; unlink closes it and clears partition data; a failed first login-window launch rolls back the provisional profile. Newly entered Web profiles do not assert a Facebook user identity, OAuth token, live API scopes, or successful sync. See `tests/unit/social/socialBridge.test.ts`, `socialSettings.dom.test.tsx`, `sessionVault.test.ts` (35/35 focused Social tests).



**CURRENT (focused code and unit/DOM tests):** Social's existing /social route and four panels are backed by typed IPC and a SQLite metadata store at `packages/desktop/src/process/services/social/socialSqliteStore.ts`. The store retains unseen feed/reel items across restarts, preserves viewed flags during resync, and deletes cached account-owned posts/reels/conversations/messages on unlink. Authorized account filtering occurs **before** SQL pagination, preventing denied accounts from occupying a page of otherwise visible content. Electron sessions use isolated account partitions, and removing an account attempts to clear its partition data and cache. Newly added account handles are not presented as authenticated sessions. Reels, inbox and threads now expose distinct, permission-gated sync operations with provider ownership checks; renderer switch-account flows discard stale async responses. Evidence: `tests/unit/social/socialDb.test.ts`, `socialBridge.test.ts`, `socialHooks.dom.test.tsx` and the remaining `tests/unit/social/` checks (32 passing unit/DOM tests across 10 Social test files on 2026-10-15).

**PARTIAL:** Refresh and read paths work against injected, authorized platform adapters; Reels playback loads only nearby players; feed/reels use viewed/unseen tracking and SQLite eviction after 48 hours. Existing social adapters are placeholders returning `SOCIAL_CONNECTOR_UNAVAILABLE` and do not pull live content. Normal login windows alone cannot establish OAuth/API permissions, true session status or send-message receipts. Cached text/metadata is counted by the SQLite store; real media file cache, per-provider schedule settings, full i18n, native-addon ABI and packaged Electron smoke/release validation remain **TARGET**. Actual provider integrations require platform-approved authentication/scopes, rate-limit and consent decisions; until then live feed/reels/DM aggregation is **BLOCKED**, not CURRENT. ## Current production seams

Several execution systems coexist:

- native conversation database and provider bridges;
- agentRuntime and agent mesh orchestration;
- company runner and multi-agent services;
- experimentalCore adapters and sessions;
- Foundation Run Kernel;
- package-contributed capabilities;
- browser, automation, and other domain-specific executors.

**PARTIAL:** These systems share some security, resource, and persistence components, but they do not all enter through one durable run state machine. This is the main architectural risk: a new adapter can appear functional while bypassing permission, egress, cancellation, evidence, or recovery policy.

## Strong foundations worth retaining

The rebuild should consolidate, not discard, these implemented assets:

- durable context records with provenance and bounded composition;
- safe-storage-backed secret handles;
- outbound secret inspection primitives;
- a mature ResourceCoordinator;
- adapter contracts for several local, cloud, CLI, and remote execution styles;
- package manifest validation and transactional install/restore mechanics;
- artifact defenses for signatures, traversal, oversized archives, and unsafe downloads;
- agent mesh evidence and orchestration components;
- typed IPC and preload patterns where already present;
- contract, integration, end-to-end, and benchmark infrastructure.

## Critical gaps

P0 and P1 below are severity/scope labels, not execution phases. C0-C6 in the [MVP master plan](../execution/mvp-plan.md) owns dependency order.

### P0: one governed run path

There is no single production entry point that every enabled release-candidate surface must use. Foundation now governs Hub, native conversation, and the `experimental-core.start` compatibility route before streaming Core execution, but domain-specific executors still bypass it. ExperimentalCoreRuntime remains production-reachable under an experimental name and still owns sessions/replay. Every remaining executor must migrate through the Foundation lifecycle or remain disabled for the release candidate.

### P0: deny-by-default trust and IPC boundary

The base needs one TrustBroker contract for origin, capability, secret handle, approval, and final egress. Every base preload method must have a schema and sender policy; unrestricted string dispatch is not an acceptable bridge. Selected inspection call sites and partially typed IPC do not establish universal coverage.

### P0: durable recovery and idempotency

Foundation now has a durable append-only journal and restart reconstruction. Universal active-run continuation, side-effect proposal/commit, compensation, and exactly-once recovery across every enabled executor and Store mutation remain incomplete.

### P0: explicit, causal, and consented user context

ContextStore, its learning coordinator, main-process learning providers, projection, and IDE-independent recovery are useful foundations. The bounded causal IPC/store contract now proves that reasonless repetition remains `needs_reason` and a reasoned correction can apply only its stated scoped fact. C3 still needs one base user journey for provenance inspection, confirmation, rejection, correction, forgetting, export, deletion, pause, and no authorization drift. Autonomous background learning is not required.

### P0: local, cloud, and CLI product paths

One offline local model, one write-only-credential cloud adapter, and one supervised CLI must pass the same Run Kernel lifecycle in ordinary Hub conversation. The user-run loopback local target is production-wired; selected cloud provider credentials remain main-process-only and enter the supervised Tomny child environment. `app-provider:*` targets validate a credential-bearing HTTPS (or loopback HTTP) endpoint and bind the selected model hostname to Foundation before that child starts. LocalInferenceBroker and ModelPack components are not yet the managed local-model production path, and exact HTTP egress inside the child still needs a Hub-owned proof.

### P0: continuous Store and package release path

Store catalog, product detail, permission consent, package installation, signed artifacts, and lifecycle fixtures are foundations, not Store completion. The S0-S6 track must continue through deterministic resolution, ordinary-payment order and entitlement, paid activation under unchanged technical trust, refund/revocation, interoperability, IDE extraction, and clean-base proof. Store work does not wait for managed AI or managed cloud.

### Independent Full managed-usage checkpoint

**TARGET:** Cloud model APIs and managed cloud compute are different targets. C6B still needs an authoritative Credit ledger, one managed-AI settlement, and one scale-to-zero compute slice. Existing account-plan credit prototypes, remote adapters, and cloud relay do not satisfy that gate. Managed switches can remain disabled without blocking a correctly reported Core plus Store candidate.

### P0: deterministic routing and one resource owner

MVP routing must deterministically use capability, privacy, an allowed pin, health, the existing ResourceCoordinator, and a hard budget. Foundation's duplicate choice and lease adapters must be removed or delegate completely to those authoritative services.

### P0: isolated package ABI and physical extraction

The versioned `host.runtime.info` package syscall, main-process capability lease, isolated sandbox runtime, and a buildable tiny signed pilot now exist. The pilot has developer-signed lifecycle evidence including restart and rollback. A production pilot release remains blocked on the committed production signing key. Browser and IDE are default base surfaces; every other optional owner must be absent and inactive in the base graph and artifact. Complete optional package lifecycles remain P1.

### P1: advanced learning and learned routing

Background inference, proactive habit learning, learned quality ranking, predictive latency, and cost optimization follow the explicit-memory and deterministic-router MVP.

### P1: provider breadth and orchestration sophistication

Additional providers, complex multi-agent strategies, and richer package capabilities follow the single local/cloud/CLI proof and stable contracts.

### P1: cross-platform parity

## Checkpoint progress reporting

Each update reports Hub, Trust/User Intelligence, Store/Package, Managed Usage, and Release as acceptance atoms: required total, passing at the current revision, failing or blocked with a named cause, enabled or disabled switches, latest command and exit code, artifact, and owner. Core plus Store and Full managed-usage percentages are separate. Release readiness is the lowest completion among the tracks required by the advertised checkpoint, not their average. Only the Integrator changes a canonical status to CURRENT.

## Evidence rules for future updates

A row becomes CURRENT only when:

1. a reachable production path exists;
2. the path uses the intended shared boundary;
3. contract or integration tests cover success and denial/failure behavior;
4. restart, cancellation, and cleanup behavior are tested where applicable;
5. packaging claims are verified against an artifact generated from the same revision rather than a stale metafile;
6. the document cites the evidence path or command and its exit code;
7. the relevant C0-C6 acceptance atom and feature-switch state are explicit.

Source presence alone supports PARTIAL, not CURRENT.
