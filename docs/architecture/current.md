# Current architecture and evidence

**Working-tree evidence snapshot:** 2026-08-22, based on the current dirty worktree rather than a release candidate. CURRENT and PARTIAL claims describe inspected code and named passing tests; release completion still requires same-revision C0 and C6 evidence.
**Purpose:** record what the repository demonstrates, not what earlier plans promised.

## Model migration status (Standardized on Laya, 2026-09-21)

**PARTIAL:** The intended topology is now standardized on the **Laya Decision Engine** (~322M/421M non-autoregressive encoder, ~33ms latency) for local security, user-understanding, and semantic-analysis. Generative autoregressive Qwen models are deprecated and removed from the target local architecture; orchestration is assigned to an API LLM. Local egress checks and composable chat pipeline stages integrate directly with Laya without queuing delays.

## Runtime shape

**CURRENT:** The primary product is an Electron desktop application under packages/desktop. It uses distinct main-process, preload, and renderer areas. Supporting workspace packages include the runtime compatibility layer, cloud relay, web host and CLI, account kit, shared scripts, and MTUI.

**CURRENT (2026-09-06 source update):** Hub, conversation and settings remain in desktop. IDE, Design and Document Studio implementation has moved to `packages/package-apps`; legacy optional domains remain in desktop source. Independent development builds and empty-root package-manager lifecycle tests pass for those three apps. This does not establish interactive UI, native runtime or AI readiness; current limitations are owned by [package extraction evidence](../platform/packages.md#source-extraction-evidence-2026-09-06).

**CURRENT:** Desktop authentication has no synthetic local account or demo login path. A real Supabase/OIDC session is required, and missing or invalid authentication remains unauthenticated. Legacy synthetic sessions persisted by earlier development builds are rejected and cleared before online validation; `accountSessionService.test.ts` and `accountAuthBridge.test.ts` cover the fail-closed and trusted-renderer boundaries.

**PARTIAL:** The repository has web and remote support, but desktop is the only product shape assessed here. Cross-platform behavior must be proven per operating system.

## Current production seams

Several execution systems coexist:

- native conversation database and provider bridges;
- agentRuntime and agent mesh orchestration;
- company runner and multi-agent services;
- experimentalCore adapters and sessions;
- Foundation Run Kernel;
- package-contributed capabilities;
- browser, automation, and other domain-specific executors.

**PARTIAL:** These systems share some security, resource, and persistence components, but they do not all enter through one durable run state machine. This is the main architectural risk: a new adapter can appear functional while bypassing permission, egress, cancellation, evidence, or recovery policy.

## Strong foundations worth retaining

The rebuild should consolidate, not discard, these implemented assets:

- durable context records with provenance and bounded composition;
- safe-storage-backed secret handles;
- outbound secret inspection primitives;
- a mature ResourceCoordinator;
- adapter contracts for several local, cloud, CLI, and remote execution styles;
- package manifest validation and transactional install/restore mechanics;
- artifact defenses for signatures, traversal, oversized archives, and unsafe downloads;
- agent mesh evidence and orchestration components;
- typed IPC and preload patterns where already present;
- contract, integration, end-to-end, and benchmark infrastructure.

## Critical gaps

P0 and P1 below are severity/scope labels, not execution phases. C0-C6 in the [MVP master plan](../execution/mvp-plan.md) owns dependency order.

### P0: one governed run path

There is no single production entry point that every enabled release-candidate surface must use. Foundation now governs Hub, native conversation, and the `experimental-core.start` compatibility route before streaming Core execution, but domain-specific executors still bypass it. ExperimentalCoreRuntime remains production-reachable under an experimental name and still owns sessions/replay. Every remaining executor must migrate through the Foundation lifecycle or remain disabled for the release candidate.

### P0: deny-by-default trust and IPC boundary

The base needs one TrustBroker contract for origin, capability, secret handle, approval, and final egress. Every base preload method must have a schema and sender policy; unrestricted string dispatch is not an acceptable bridge. Selected inspection call sites and partially typed IPC do not establish universal coverage.

### P0: durable recovery and idempotency

Foundation now has a durable append-only journal and restart reconstruction. Universal active-run continuation, side-effect proposal/commit, compensation, and exactly-once recovery across every enabled executor and Store mutation remain incomplete.

### P0: explicit, causal, and consented user context

ContextStore, its learning coordinator, main-process learning providers, projection, and IDE-independent recovery are useful foundations. The bounded causal IPC/store contract now proves that reasonless repetition remains `needs_reason` and a reasoned correction can apply only its stated scoped fact. C3 still needs one base user journey for provenance inspection, confirmation, rejection, correction, forgetting, export, deletion, pause, and no authorization drift. Autonomous background learning is not required.

### P0: local, cloud, and CLI product paths

One offline local model, one write-only-credential cloud adapter, and one supervised CLI must pass the same Run Kernel lifecycle in ordinary Hub conversation. The user-run loopback local target is production-wired; selected cloud provider credentials remain main-process-only and enter the supervised Tomny child environment. `app-provider:*` targets validate a credential-bearing HTTPS (or loopback HTTP) endpoint and bind the selected model hostname to Foundation before that child starts. LocalInferenceBroker and ModelPack components are not yet the managed local-model production path, and exact HTTP egress inside the child still needs a Hub-owned proof.

### P0: continuous Store and package release path

Store catalog, product detail, permission consent, package installation, signed artifacts, and lifecycle fixtures are foundations, not Store completion. The S0-S6 track must continue through deterministic resolution, ordinary-payment order and entitlement, paid activation under unchanged technical trust, refund/revocation, interoperability, IDE extraction, and clean-base proof. Store work does not wait for managed AI or managed cloud.

### Independent Full managed-usage checkpoint

**TARGET:** Cloud model APIs and managed cloud compute are different targets. C6B still needs an authoritative Credit ledger, one managed-AI settlement, and one scale-to-zero compute slice. Existing account-plan credit prototypes, remote adapters, and cloud relay do not satisfy that gate. Managed switches can remain disabled without blocking a correctly reported Core plus Store candidate.

### P0: deterministic routing and one resource owner

MVP routing must deterministically use capability, privacy, an allowed pin, health, the existing ResourceCoordinator, and a hard budget. Foundation's duplicate choice and lease adapters must be removed or delegate completely to those authoritative services.

### P0: isolated package ABI and physical extraction

The versioned `host.runtime.info` package syscall, main-process capability lease, isolated sandbox runtime, and a buildable tiny signed pilot now exist. The pilot has developer-signed lifecycle evidence including restart and rollback. A production pilot release remains blocked on the committed production signing key. Browser and IDE are default base surfaces; every other optional owner must be absent and inactive in the base graph and artifact. Complete optional package lifecycles remain P1.

### P1: advanced learning and learned routing

Background inference, proactive habit learning, learned quality ranking, predictive latency, and cost optimization follow the explicit-memory and deterministic-router MVP.

### P1: provider breadth and orchestration sophistication

Additional providers, complex multi-agent strategies, and richer package capabilities follow the single local/cloud/CLI proof and stable contracts.

### P1: cross-platform parity

Desktop-first MVP evidence can target an explicitly named platform. Other operating systems become CURRENT only after equivalent security, package-isolation, local-runtime, and release evidence.

## Checkpoint progress reporting

Each update reports Hub, Trust/User Intelligence, Store/Package, Managed Usage, and Release as acceptance atoms: required total, passing at the current revision, failing or blocked with a named cause, enabled or disabled switches, latest command and exit code, artifact, and owner. It also identifies the active C0-C6 checkpoint and S0-S6 Store slice.

Core plus Store and Full managed-usage percentages are separate. Release readiness is the lowest completion among the tracks required by the advertised checkpoint, not their average. Only the Integrator changes a canonical status to CURRENT.

## Evidence rules for future updates

A row becomes CURRENT only when:

1. a reachable production path exists;
2. the path uses the intended shared boundary;
3. contract or integration tests cover success and denial/failure behavior;
4. restart, cancellation, and cleanup behavior are tested where applicable;
5. packaging claims are verified against an artifact generated from the same revision rather than a stale metafile;
6. the document cites the evidence path or command and its exit code;
7. the relevant C0-C6 acceptance atom and feature-switch state are explicit.

Source presence alone supports PARTIAL, not CURRENT.
